```python
"""The Read the Docs site builds without warnings and cannot drift from what the tool does (nuisance presets,
recipes, the example model). Sources are in docs/source/; the pages are for students."""
import importlib.util
import re
import shutil
import subprocess
import sys
from pathlib import Path

import pytest

ROOT = Path(__file__).resolve().parent.parent
SRC = ROOT / "docs" / "source"
REQS = ROOT / "docs" / "requirements.txt"
PAGES = sorted(SRC.rglob("*.md"))


def _sphinx_cmd():
    """Sphinx from this interpreter when the docs packages are installed, else through uv (it installs them for the run)."""
    if all(importlib.util.find_spec(m) for m in ("sphinx", "myst_parser", "shibuya")):
        return [sys.executable, "-m", "sphinx"]
    if shutil.which("uv"):
        return ["uv", "run", "--no-project", "--with-requirements", str(REQS), "python", "-m", "sphinx"]
    return None


@pytest.fixture(scope="module")
def html(tmp_path_factory):
    cmd = _sphinx_cmd()
    if cmd is None:
        pytest.skip("neither the docs packages (docs/requirements.txt) nor uv is available")
    out = tmp_path_factory.mktemp("docs_html")
    proc = subprocess.run(cmd + ["-W", "--keep-going", "-q", "-b", "html", str(SRC), str(out)],
                          capture_output=True, text=True, timeout=900)
    return proc, out


def test_rtd_config_points_at_the_site():
    rtd = (ROOT / ".readthedocs.yaml").read_text()
    assert re.search(r"^version: 2$", rtd, re.M)
    assert "configuration: docs/source/conf.py" in rtd
    assert re.search(r"fail_on_warning: true", rtd)
    assert "requirements: docs/requirements.txt" in rtd
    assert (SRC / "conf.py").is_file() and REQS.is_file()


def test_site_builds_without_warnings(html):
    proc, out = html
    assert proc.returncode == 0, (proc.stdout + proc.stderr)[-3000:]
    assert (out / "index.html").is_file()


def test_no_lab_study_or_local_paths_in_the_pages():
    pattern = re.compile(r"study 141|\bcrom\b|sub-141|/data/local|/home/mri", re.I)
    hits = [f"{p.relative_to(SRC)}: {m.group()}" for p in PAGES for m in pattern.finditer(p.read_text())]
    assert not hits, hits
```

````markdown
# fMRIPrep must be finished

This tool does **no preprocessing**. It starts from the output of [fMRIPrep](https://fmriprep.org/). bidspm can also
preprocess with SPM, but this runner does not use that: the steps it runs are smoothing, first-level statistics and
group-level statistics.

## What "ready" means

For every subject and every run of the task you want to analyse, the fMRIPrep output folder must contain, under
`sub-<label>/func/` (or `sub-<label>/ses-<n>/func/`):

| File (pattern) | Used for |
|---|---|
| `*task-<task>_*space-<space>_*desc-preproc_bold.nii.gz` | the preprocessed BOLD series that gets smoothed and analysed |
| `*task-<task>_*desc-confounds_timeseries.tsv` (and its `.json`) | nuisance regressors such as motion, see The confounds file |
| `*task-<task>_*space-<space>_*desc-brain_mask.nii.gz` | the brain mask that limits the analysis to brain voxels |

`<space>` is the output space in the file name, for example `MNI152NLin2009cAsym`. The **Space** setting of your project must
be exactly that string, and all subjects must have the same space. If a subject has no preprocessed BOLD in that space, the
readiness check stops with *"has no preprocessed BOLD for task-… in space …"* and tells you to re-run fMRIPrep with
`--output-spaces <space>`.

## If you only have raw data

Run fMRIPrep first. It is a separate program with its own documentation and its own citation (see
[Credits and citing](../credits.md)); running it is outside this tool.

## What the tool does with it

Your fMRIPrep folder is read, never changed. The smoothing step writes into the `bidspm-preproc/` folder of your
working directory: a copy of the preprocessed BOLD, the smoothed BOLD (`desc-smth<FWHM>_bold`), the brain mask and a copy of the
confounds file. The statistics step then reads only `bidspm-preproc/`. The gears page shows where everything lives.
````

````markdown
# The confounds file

For every run, fMRIPrep writes a table of nuisance signals next to the preprocessed data:

```text
sub-<label>/func/sub-<label>_task-<task>_desc-confounds_timeseries.tsv
sub-<label>/func/sub-<label>_task-<task>_desc-confounds_timeseries.json
```

The `.tsv` has **one row per volume** and **one column per signal**; the `.json` describes the columns. You can open the
`.tsv` in any spreadsheet program or `head` it in a terminal.

## What is in it

| Column(s) | Meaning |
|---|---|
| `trans_x`, `trans_y`, `trans_z` | head translation in mm (the three motion axes) |
| `rot_x`, `rot_y`, `rot_z` | head rotation in radians |
| `framewise_displacement` | how far the head moved between two volumes |
| `*_derivative1`, `*_power2`, `*_derivative1_power2` | the motion columns' temporal derivative, square and squared derivative |
| `a_comp_cor_*`, `global_signal`, `csf`, `white_matter`, ... | physiological and tissue signals |

The first row of derivative columns and of `framewise_displacement` is `n/a`: there is no previous volume to compare with.
That is normal.

## Why the model needs it

Head motion produces signal changes that look like activation. Adding the motion signals to the model as **nuisance
regressors** removes the part of the signal they explain. In the BIDS Stats Model they are the column names listed after the
intercept (`1`) in `X`, see The BIDS Stats Model.

## The wizard's presets

The model wizard offers these presets in its nuisance step. The default is `none`.

| Preset | Columns |
|---|---|
| `none` | no nuisance regressors |
| `motion6` | `trans_x`, `trans_y`, `trans_z`, `rot_x`, `rot_y`, `rot_z` |
| `motion24` | `motion6` plus, for each of the six, `_derivative1`, `_power2` and `_derivative1_power2` (24 columns) |
| `motion6_fd` | `motion6` plus `framewise_displacement` |

Instead of a preset you can type your own comma-separated list of column names. A name that fMRIPrep did not write is
reported as a warning in the wizard and as a problem by the readiness check.

## What the tool does with the file

The smoothing step copies the confounds file (`.tsv` and `.json`) from fMRIPrep into `bidspm-preproc/`, because the statistics step
reads only that folder. This copy matters: the engine itself only logs a warning when it cannot find a confounds file, so
a model once ran **without motion regressors** and nobody noticed. The copy is now always made, and the readiness check
reports these as errors before a run starts:

- no confounds file for a run when the model uses nuisance columns;
- a confounds file that does not have the same number of rows as the BOLD has volumes (it belongs to another run);
- non-numeric values (other than `n/a`).

The fix is nearly always the same: re-run fMRIPrep for that subject.
````

````markdown
The events file is your **paradigm**: what happened, when, and for how long. It belongs to the raw
[BIDS](https://bids.neuroimaging.io/) dataset, not to fMRIPrep:

```text
rawdata/sub-<label>/func/sub-<label>_task-<task>_run-<n>_events.tsv
```

It is a **tab-separated** text file, one row per event (a trial, a block, a button press).

## Columns

| Column | Required | Meaning |
|---|---|---|
| `onset` | yes | seconds from the start of the run (the first volume) to the start of the event |
| `duration` | yes | seconds the event lasted; `0` is allowed for instantaneous events |
| `trial_type` | for the wizard | the condition name, for example `congruent` |
| anything else | no | extra information per event, for example `response_validity` or `rt` |

```text
onset	duration	trial_type	response_validity	rt
10.0	2.0	congruent	valid	0.52
14.0	2.0	incongruent	invalid	n/a
```

`n/a` marks a missing value. It is allowed in the extra columns but **not** in `onset` or `duration`.

## One file per run, or one for all

The tool uses the most specific events file that applies to a run. If a subject has no events file of its own, the
dataset-level file `task-<task>_events.tsv` in the top folder of the dataset is used (BIDS inheritance). The file must not
quote its fields.

## What the tool does with it

- The **model wizard** reads the events of all subjects. The `trial_type` values become the conditions you can keep or
  leave out; the other columns are what recipes work on, for example `split_by_column` splits a condition by
  `response_validity`, `parametric_modulator` uses a numeric column such as `rt`. See
  The BIDS Stats Model.
- The **readiness check** reads them before a run and reports, per subject:
  - no events file for the task;
  - no `onset` or `duration` column, a duplicate column, or a file that is not UTF-8 text;
  - an `onset` or `duration` that is not a number, or a negative `duration` (the row is named by its line number);
  - a negative onset (a warning: BIDS allows it, but check that the events are aligned to the scan);
  - events that run past the end of the scan (a warning);
  - a condition that the model uses but a subject never has.

## Things that go wrong

- A column you filter or modulate on that is `n/a` in every row makes the analysis fail for that subject; the wizard flags such
  columns.
- Events in milliseconds instead of seconds give a model that fits nothing.
- A condition name with spaces or other special characters: the wizard allows letters, digits, `_` and `-` only.
````

````markdown
# The BIDS Stats Model

**This is the file that decides what is analysed.** The events file says what happened in the scanner and the confounds file
says how the head moved; the *model* says which of that goes into the analysis, what to compare with what, and how the
runs, subjects and the group are combined. Get this file right and everything else is routine.

It is a JSON file that follows the [BIDS Stats Models](https://bids-standard.github.io/stats-models/) specification. The
analysis itself is done by [bidspm](https://bidspm.readthedocs.io/en/latest/), which reads this file and turns it into SPM
batches; its documentation describes every field. This page teaches the parts you need.

## The idea in one picture

A model has `Nodes`, one per analysis level, joined by `Edges`:

```text
Run node  ──►  Subject node  ──►  Dataset node
(one run of     (average the        (one-sample t test
 one subject)    runs of a subject)  across subjects)
```

## A complete example

The file below is generated by the model wizard from a task `demo` with two conditions, `faces` and `houses`, the
`motion6` nuisance preset and one extra comparison, `faces_gt_houses`. It is a real model, not a sketch.

```{literalinclude} ../_examples/faces_houses_model.json
:language: json
```

## Reading it

**Top of the file**

- `Name`: a label, also used for output names. `BIDSModelVersion` and `Description`: bookkeeping.
- `Input`: which data the model applies to. Here `{"task": ["demo"]}`. The output **space** is *not* in the model: it is the
  Space setting of your project, and it has to match the `space-` in your fMRIPrep file names
  (see [fMRIPrep must be finished](fmriprep.md)).

**The Run node** (`"Level": "Run"`) fits the GLM to one run of one subject.

- `GroupBy: ["run", "subject"]`: one model per run and subject.
- `Model.X`: the **design matrix columns**, in this order: the conditions
  (`trial_type.faces`: the value `faces` of the events column `trial_type`), then `1` (the intercept, always there), then the
  nuisance columns from [the confounds file](confounds.md).
- `Model.HRF.Variables`: which columns are convolved with the haemodynamic response. The conditions are; the nuisance columns are
  not.
- `Model.Options`: `HighPassFilterCutoffHz` (the temporal filter) and `Mask` (use fMRIPrep's brain mask).
- `Model.Software.SPM.SerialCorrelation`: how SPM models the temporal autocorrelation (`FAST` here).
- `Contrasts`: the comparisons. Each has a `Name`, a `ConditionList` (which design columns take part), `Weights` (one number per
  listed column) and a `Test` (`t`). `faces` with weight `1` tests "faces against baseline"; `faces_gt_houses` with weights `1, -1`
  tests "more for faces than for houses". Weights of a difference sum to zero.

**The Subject node** averages a subject's runs. It carries the same contrasts forward. **The Dataset node** is the group level:
a one-sample t test per contrast across subjects (`DummyContrasts` names which contrasts to test).

**Edges** connect the nodes; the second edge's `Filter` says which contrasts move up to the group level.

## How names flow through the analysis

A condition name travels from your data to your results, and every link has to match:

```text
events file:   trial_type = faces
model:         trial_type.faces  (in X, HRF.Variables and in a contrast's ConditionList)
SPM:           a regressor called faces
contrast:      Name "faces" (or faces_gt_houses)  ->  con_NNNN.nii and spmT_NNNN.nii for each subject
group:         one result per contrast name
```

If you rename a condition in the events file, or delete it from `X`, a contrast that still lists it points at nothing; the
readiness check reports this (*"has no events for …"*) before the run starts.

## How to make a model

1. **The model wizard** (recommended). *New model* on the analysis page opens five steps: task and conditions, recipes, nuisance,
   contrasts, review and save. It reads the events files of your project, so you only pick from what exists. Recipes
   reshape the conditions:
   - `valid_only`: keep only some trials, for example only rows where `response_validity` is `valid`;
   - `split_by_column`: split a condition by a column, for example `item` into `valid_item` and `invalid_item`;
   - `merge_rename`: merge or rename conditions, for example `a, b -> ab`;
   - `parametric_modulator`: modulate a regressor by a numeric column such as `rt` (polynomial order 1 to 3); add it last.

   Recipes write `Transformations` into the Run node; they are applied in the order you added them.
2. **The model editor** (with its contrast builder) for what the wizard does not write: weighted contrasts and F contrasts.
3. **By hand.** Any editor works; the readiness check tells you what is wrong.

## Where the file lives and how it is chosen

- The wizard saves to `models/` inside your **derivatives** folder (inside the working directory when you left derivatives
  empty), for example `<working directory>/models/faces_houses.json`.
- A project stores the model it uses. On the command line it is the `MODELS_FILE` setting of the configuration file, or
  `--model <file>` for one run. A bare file name is looked up in `models/` first for the setting, and in the current folder
  first for `--model`; a full path is used as it is.
- The **task** in the model's `Input` must exist in your dataset, and the conditions it names must exist in the events.

## What is checked before a run

The runner validates the file against the BIDS Stats Models schema before anything starts, and the readiness check goes
further: it compares the model with your actual data. Typical messages:

- *Invalid JSON* or *Model file not found*: the file itself.
- *Empty contrast issues*: a contrast with no conditions or no weights.
- *has no events for …*: a condition in the model that a subject never has.
- *has no confounds file …*: the model uses nuisance columns that a run lacks.

Fix the data or the model, run the check again, and only then start the run.
````
