# The BIDS Stats Model

**This is the file that decides what is analysed.** The events file says what happened in the scanner and the confounds file
says how the head moved; the *model* says which of that goes into the analysis, what to compare with what, and how the
runs, subjects and the group are combined. Get this file right and everything else is routine.

It is a JSON file that follows the [BIDS Stats Models](https://bids-standard.github.io/stats-models/) specification. The
analysis itself is done by [bidspm](https://bidspm.readthedocs.io/en/latest/), which reads this file and turns it into SPM
batches; its documentation describes every field. This page teaches the parts you need.

## The idea in one picture

A model has `Nodes`, one per analysis level, joined by `Edges`:

```text
Run node  ──►  Subject node  ──►  Dataset node
(one run of     (average the        (one-sample t test
 one subject)    runs of a subject)  across subjects)
```

## Reading it

**Top of the file**

- `Name`: a label, also used for output names. `BIDSModelVersion` and `Description`: bookkeeping.
- `Input`: which data the model applies to. Here `{"task": ["demo"]}`. The output **space** is *not* in the model: it is the
  Space setting of your project, and it has to match the `space-` in your fMRIPrep file names
  (see [fMRIPrep must be finished](fmriprep.md)).

**The Run node** (`"Level": "Run"`) fits the GLM to one run of one subject.

- `GroupBy: ["run", "subject"]`: one model per run and subject.
- `Model.X`: the **design matrix columns**, in this order: the conditions
  (`trial_type.faces`: the value `faces` of the events column `trial_type`), then `1` (the intercept, always there), then the
  nuisance columns from [the confounds file](confounds.md).
- `Model.HRF.Variables`: which columns are convolved with the haemodynamic response. The conditions are; the nuisance columns are
  not.
- `Model.Options`: `HighPassFilterCutoffHz` (the temporal filter) and `Mask` (use fMRIPrep's brain mask).
- `Model.Software.SPM.SerialCorrelation`: how SPM models the temporal autocorrelation (`FAST` here).
- `Contrasts`: the comparisons. Each has a `Name`, a `ConditionList` (which design columns take part), `Weights` (one number per
  listed column) and a `Test` (`t`). `faces` with weight `1` tests "faces against baseline"; `faces_gt_houses` with weights `1, -1`
  tests "more for faces than for houses". Weights of a difference sum to zero.

**The Subject node** averages a subject's runs. It carries the same contrasts forward. **The Dataset node** is the group level:
a one-sample t test per contrast across subjects (`DummyContrasts` names which contrasts to test).

**Edges** connect the nodes; the second edge's `Filter` says which contrasts move up to the group level.

## How names flow through the analysis

A condition name travels from your data to your results, and every link has to match:

```text
events file:   trial_type = faces
model:         trial_type.faces  (in X, HRF.Variables and in a contrast's ConditionList)
SPM:           a regressor called faces
contrast:      Name "faces" (or faces_gt_houses)  ->  con_NNNN.nii and spmT_NNNN.nii for each subject
group:         one result per contrast name
```

If you rename a condition in the events file, the model still asks for the old name. For a model **without recipes** (no
`Transformations` in the Run node), and when the run includes the statistics step, the readiness check reports this before
the run starts (*"condition '…' is in the model but in none of the … events files"*, or *"has no events for …"* when only some
subjects lack it). For a model built with the `valid_only`, `split_by_column` or `merge_rename` recipes the check does not
compare condition names, so after any rename check the condition names in the events files by hand. The check reads the
conditions from `X`, so keep `X`, `HRF.Variables` and every contrast's `ConditionList` in
step by hand: a contrast that still lists a condition you removed from `X` points at nothing.

## How to make a model

1. **The model wizard** (recommended). *New model* on the analysis page opens five steps: task and conditions, recipes, nuisance,
   contrasts, review and save. It reads the events files of your project, so you only pick from what exists. Recipes
   reshape the conditions:
   - `valid_only`: keep only some trials, for example only rows where `response_validity` is `valid`;
   - `split_by_column`: split a condition by a column, for example `item` into `valid_item` and `invalid_item`;
   - `merge_rename`: merge or rename conditions, for example `a, b -> ab`;
   - `parametric_modulator`: modulate a regressor by a numeric column such as `rt` (polynomial order 1 to 3); add it last.

   Recipes write `Transformations` into the Run node; they are applied in the order you added them.
2. **The model editor** (with its contrast builder) for what the wizard does not write: weighted contrasts and F contrasts.
3. **By hand.** Any editor works; the readiness check tells you what is wrong.

## Where the file lives and how it is chosen

- The wizard saves to `models/` inside your **derivatives** folder (inside the working directory when you left derivatives
  empty), for example `<working directory>/models/faces_houses.json`.
- A project stores the model it uses. On the command line it is the `MODELS_FILE` setting of the configuration file, or
  `--model <file>` for one run. A bare file name is looked up in `models/` first for the setting, and in the current folder
  first for `--model`; a full path is used as it is.
- The **task** in the model's `Input` must exist in your dataset, and the conditions it names must exist in the events.

## What is checked before a run

The runner validates the file against the BIDS Stats Models schema before anything starts, and the readiness check goes
further: it compares the model with your actual data. Typical messages:

- *Invalid JSON* or *Model file not found*: the file itself.
- *Empty contrast issues*: a contrast with no conditions or no weights.
- *has no events for …*: a condition in the model that a subject never has.
- *has no confounds file …*: a run of a subject has no confounds file, which the nuisance columns need. A file that exists but
  lacks a nuisance column is reported as *lacks the model's regressors*.

Fix the data or the model, run the check again, and only then start the run.
